# PR 기반 업무 관리

관리 대화는 개선 항목을 찾아 먼저 등록하고, 개발 대화가 각각 이어 구현하는 동안 다음 항목을 찾는다. 한 항목을 직접 구현한 뒤 다음 항목을 찾는 순차 개발 흐름으로 바꾸지 않는다. 개별 업무의 SSOT는 PR 본문이다. 여기서 PR은 호스팅 서비스의 Merge Request도 포함한다.

이 폴더만 다른 저장소의 스킬 경로로 복사해 사용할 수 있다. 프로젝트 설정 파일이나 특정 앱·다른 스킬을 설치해야만 작동하는 구조를 만들지 않는다. 사용자 지시와 대상 저장소의 지침이 이 스킬의 기본 운영 방식보다 우선한다.

## 대상 프로젝트 결정

사용자가 지정한 저장소와 현재 작업 폴더의 Git 원격을 확인해 대상 호스트·저장소를 결정한다. fork의 개인 원격과 통합 대상 저장소를 혼동하지 않는다. 통합 브랜치, 작업 브랜치 이름 규칙, 커밋 언어, 제품·개발 판단 기준은 대상 프로젝트의 `AGENTS.md` 등 적용되는 지침에서 읽는다. 지침이 없다면 통합 브랜치는 원격 기본 브랜치를 사용하고 나머지는 현재 사용자 언어와 저장소 관례를 따른다. 원격이나 통합 대상이 여러 개라 결정할 수 없을 때만 확인한다.

프로젝트에 계약 문서가 있으면 그 문서를 사용하되 특정 파일명이나 구조를 가정하지 않는다. 적용 지침을 찾지 못했다고 임의의 제품 계약을 만들어 넣지 않는다. 프로젝트 전용 설정을 이 스킬에 복제하지 않는다.

## 진행 작업 파악

명시적인 조회 요청이 없어도 시작할 때 열린 PR과 관련 본문·댓글·실제 diff를 읽는다. 대상 호스트에 맞는 연결 도구나 CLI를 사용한다. CLI의 기본 대상이 확인한 통합 저장소와 같은지 확인하고, fork 등으로 다르면 조회·생성·갱신 명령에 대상 저장소를 명시한다. GitHub라면 대상이 일치하는 체크아웃에서 다음 조회를 출발점으로 사용할 수 있다. 다른 호스트에서는 해당 서비스의 같은 조회 기능을 사용한다.

```powershell
gh pr list --state open --json number,title,body,headRefName,url,isDraft
```

열린 PR만으로 현재 작업을 판단하지 않는다. 사용 가능한 대화 조회 도구로 같은 저장소의 진행 대화를 읽고, 로컬 브랜치·worktree·미커밋 변경도 확인한다. 대화 목록이 없으면 확인 가능한 근거를 사용하고 그 한계를 밝힌다. 원격 브랜치는 관련 PR의 상태와 추가 작업 흔적을 함께 봐야 하며, 머지 후 남은 브랜치를 모두 진행 중이라고 취급하지 않는다.

파일명이 같다는 이유로 모든 작업을 막거나, 줄이 다르다는 이유로 독립적이라고 판단하지 않는다. 수정 함수·모듈·스키마·상태 소유자·공통 계약·호출 관계를 비교해 이미 맡은 영역을 피한다. 조회 실패를 작업 없음으로 해석하지 않는다.

## 개선 항목 발굴과 등록

현재 코드와 사용자 의도에서 근거를 찾고, 다른 개발 대화가 해결 방향을 이해할 만큼 조사한다. 실제 관찰, 추출 메서드의 격리 재현, 코드 경로 추론을 구별한다. 일반적인 리팩터링 목록이나 추측한 기능을 수량을 채우기 위해 등록하지 않는다. 단순 결함뿐 아니라 프로젝트의 개발 방향에 맞는 구조·성능·사용 경험 개선도 후보가 될 수 있다.

독립 항목은 확인한 최신 통합 브랜치에서 작업 브랜치와 연결된 worktree를 확보하고 Draft PR을 먼저 연다. 사용할 수 있는 worktree 관리 도구가 있으면 등록된 경로를 사용하고, 사용할 수 없으면 Git worktree로 만든다. 대상 저장소와 Git 공통 디렉터리를 공유하는지 확인한다. 사용자 지시 없이 독립 clone을 만들거나 다른 대화가 사용하는 주 작업 폴더의 브랜치를 바꾸지 않는다. worktree 생성이 막히면 같은 작업을 주 폴더에서 시작하지 말고 해결한 경로 또는 남은 장애를 보고한다.

서비스가 등록 커밋을 요구하면 프로젝트 관례에 맞는 메시지의 빈 커밋을 사용할 수 있다. 계획 파일이나 가짜 코드 변경은 넣지 않는다. 해당 호스트에서 빈 커밋을 포함한 Draft 생성이 불가능하면 브랜치와 생성 장애를 보고하고 등록 완료로 처리하지 않는다. 등록 직전에 목록을 다시 조회해 조사하는 동안 다른 대화가 먼저 등록한 항목과 중복되지 않는지 확인한다.

이미 등록된 업무와 같은 목적이면 기존 본문에 반영한다. 미머지 A의 구현이 있어야 성립하는 후속 항목은 A의 PR에 포함해 담당 개발 대화가 같은 브랜치에 추가 커밋하도록 인계한다. 목적은 다르지만 같은 내부를 수정해야 한다면 경계를 좁히거나 보류한다. 단지 둘 다 미완료라는 이유로 의존하지 않는 업무를 묶지 않는다.

본문은 문제의 원인과 개선 의도가 이어지는 자연스러운 문장으로 쓴다. 작업 범위·기대 동작·완료 조건·검증 계획 같은 항목 구분이나 고정 템플릿은 만들지 않는다. 중요한 코드 경계와 의존성은 필요한 만큼 문장에 설명하고, 당연한 검증 체크리스트는 넣지 않는다. 예상하기 어려운 실패 경로나 회귀 위험을 발견했을 때 그 이유를 적는다. 담당이 없으면 미배정과 대기 상태를 짧게 남기며, 등록한 관리 대화도 식별할 수 있게 한다.

등록한 PR은 코드가 없는 업무 예약이다. 완료된 구현이나 검증된 독립성으로 보고하지 않는다. 현재까지 확인한 근거와 특별한 미확인 사항을 정확히 설명한다. PR 생성이 실패하면 푸시한 브랜치와 남은 단계를 알려주고 등록 완료로 처리하지 않는다. 현재 환경에 PR 연결 도구가 있으면 그 도구의 지침에 따라 생성한 PR을 관리 대화에 연결한다. 연결 도구가 없어도 PR 링크로 인계할 수 있다.

## 담당 배정과 개발 인계

등록 요청만 받았다면 미배정 상태로 둔다. 배정 요청을 받으면 사용자가 지정한 PR·개발 대화와 그 대화의 기존 작업을 확인한다. 대상이 여러 개라 특정할 수 없을 때만 확인한다. 하나의 작업에 개발 담당은 한 대화로 유지하며, 이미 담당자가 있으면 그 대화의 진행 상태와 인계를 확인한다.

배정 직전에 최신 본문과 담당 상태를 다시 읽고 담당 대화 ID 또는 링크, 작업 브랜치, worktree 절대 경로를 함께 기록한다. 등록용 worktree를 개발자에게 인계하면 그 시점부터 개발자가 수정·커밋을 소유한다. 같은 호스팅 계정의 assignee나 Draft 상태는 대화별 예약을 보장하지 않는다. 갱신 후 본문을 다시 읽어 다른 관리 대화의 배정과 엇갈리지 않았는지 확인한다. 담당이 달라졌다면 덮어쓰거나 개발을 촉발하지 말고 중복 배정 사실을 알려 담당을 조율한다. 재조회만으로 동시 갱신을 막을 수 있다고 가정하지 않는다. 개발이 실제로 시작된 것이 확인되기 전에는 개발 중이라고 단정하지 않고, 대기 상태에 배정 사실을 적는다.

사용자가 해당 대화에 메시지를 보내거나 새 대화를 만들도록 지시한 경우에만 그 도구를 사용한다. 배정 기록 자체를 다른 대화로 메시지를 보낼 권한으로 확대하지 않는다. 권한이 없으면 본문에 배정을 기록하고 사용자가 전달할 PR 링크를 제공한다. 자동으로 개발 대화를 생성하거나 구현을 시작하지 않는다.

인계에는 PR 링크·작업 브랜치·worktree 절대 경로를 전달하고 모든 수정 명령이 그 경로에서 실행되도록 지시한다. 개발자는 실제 경로와 브랜치, `git rev-parse --git-common-dir`의 절대 경로를 배정 정보와 비교한다. 같은 원격 URL을 가진 독립 clone도 Git 공통 디렉터리는 다르다. worktree의 `.git`는 포인터 파일일 수 있으므로 임시 본문이나 검증 파일은 시스템 임시 폴더 또는 확인한 Git 공통 디렉터리의 전용 위치에 둔다. 본문의 계획을 별도 메시지나 파일에 복제하지 않는다. 기존 브랜치의 미푸시·미커밋 변경이 있는 인계는 그 작업을 보존한다.

여러 하위 에이전트가 동시에 수정하면 각자 worktree와 임시 로컬 브랜치를 사용하고 PR 브랜치의 통합·커밋·푸시는 한 담당이 소유한다. 임시 브랜치를 별도 PR이나 원격 브랜치로 무조건 늘리지 않는다. 읽기 전용 조사는 같은 작업 내용을 조회할 수 있다. 기준 브랜치의 새 커밋을 확인할 때마다 모든 작업·검증 브랜치에 merge하지 말고, 충돌 해결이나 필요한 통합 검증 때 담당자가 반영한다.

## 관리 지속

현재 의도·담당·상태는 본문에 유지하고, 착수·인계·변경 이유 등의 이력은 댓글에 남긴다. 범위를 바꿨으면 본문도 갱신한다. 개발 중 다른 항목과 공통 계약을 공유해야 한다는 사실이 드러나면 등록 당시의 독립성 판단을 고집하지 말고, 담당 경계를 다시 정하고 관련 PR에 반영한다.

관리 대화는 그동안 겹치지 않는 다음 항목을 찾는다. 진행 확인과 후속 연락은 사용자가 요청한 범위에서 수행하고, 별도 요청 없이 반복 자동화나 지속 감시를 만들지 않는다. 리뷰·머지를 요청받으면 대상 프로젝트의 절차와 사용 가능한 전용 스킬을 따른다. 전용 스킬이 없어도 이 관리 스킬이 임의의 머지 방식이나 승인 규칙을 추가하지 않는다. 등록·배정 요청을 머지나 배포 권한으로 확대하지 않는다.

머지 후에는 프로젝트의 정리 절차에 따라 담당 작업과 임시 통합 worktree·로컬 브랜치의 처리를 확인한다. 진행 중인 worktree와 미반영 변경, 앱이 관리하는 복구 참조를 임의로 지우지 않는다. worktree는 작업 파일을 격리하지만 Git 참조와 이력은 공유한다. 그래프를 설명할 때 통합 브랜치 이력, 활성 작업, 완료된 원격 브랜치, 복구 참조를 구별한다. 원격 브랜치 삭제나 공개 이력 재작성은 등록·배정 권한에 포함하지 않는다.

전달할 때는 등록·배정한 PR 링크와 현재 담당/상태를 짧게 설명한다. 코드가 없는 Draft PR은 등록 완료라고 표현하고 개발 완료와 구별한다. 별도 인벤토리 문서를 만들지 않는다.
